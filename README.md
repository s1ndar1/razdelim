# Разделим

«Разделим» помогает небольшой компании организовать общий сбор на досуг: выбрать способ оплаты, отправить участникам ссылку в MAX, получить подтверждения и посмотреть остаток. MVP рассчитан на организатора встречи, который собирает деньги на совместное мероприятие, например поход, поездку или спортивную активность.

## Проблемная гипотеза и сценарий

Гипотеза для проверки: организатор небольшой компании отдельно рассчитывает доли, рассылает реквизиты, вручную отмечает переводы и отвечает на вопросы о статусе. Это не подтверждено интервью или отраслевой статистикой в материалах MVP; перед пилотом гипотезу нужно проверить разговорами с организаторами и разбором их текущего процесса. MVP собирает создание сбора, присоединение участника и отметку об оплате в одном сценарии MAX.

1. Пользователь запускает бота и открывает мини-приложение «Разделим».
2. Организатор задаёт название, цель сбора, число участников, реквизиты и способ оплаты: «Поровну» либо «Своя сумма».
3. Организатор отправляет ссылку участникам в MAX.
4. Участник открывает ссылку, видит равную долю или остаток и реквизиты, затем подтверждает перевод либо вводит свой взнос.
5. Организатор открывает статус сбора и видит количество участников и подтверждений.

Отметка «Я оплатил» является самоотчётом участника. MVP не проводит платежи и не подтверждает поступление денег в банке.

В режиме «Поровну» цель делится на равные доли с точностью до копейки; остаточные копейки распределяются между первыми долями. В режиме «Своя сумма» участник указывает взнос не больше остатка. После подтверждения остаток уменьшается; сбор закрывается при достижении цели. В обоих режимах подтверждение фиксирует самоотчёт участника, а не факт получения денег.

Ожидаемый эффект — сократить ручные расчёты долей, сверку статусов и повторные вопросы организатору. На пилоте сравниваются время на создание/ведение одного сбора, число ручных уточнений и доля участников, завершивших отметку статуса; исходный уровень и целевые значения фиксируются до запуска, здесь они не выдаются за измеренные результаты.

## Запуск

Требуется Docker с Compose v2. Скопируйте `.env.example` в `.env`, задайте уникальные `POSTGRES_PASSWORD`, `BOT_TOKEN`, `BOT_NAME` и `MAX_WEBHOOK_SECRET`, затем запустите все локальные компоненты одной командой:

```bash
docker compose up --build -d
```

Проверка запуска:

```bash
curl http://localhost:8000/health
```

Ожидаемый ответ: `{"status":"ok","db":"ok"}`. Веб-интерфейсы: `http://localhost:8000/`, `/organizer` и `/status`. Остановить компоненты: `docker compose down`. Повторный запуск без пересборки: `docker compose up -d`. Для полного удаления тестовой базы вместе с данными используйте `docker compose down -v`.

Секреты нельзя коммитить. `.env` игнорируется Git; в репозитории хранится только `.env.example`. Если рабочий токен когда-либо попадал в историю Git, его необходимо отозвать и выпустить заново.

### Локальная демонстрация без MAX

Только для тестовой ветки и только на loopback-интерфейсе можно пройти сценарий без бота и MAX `initData`. Запустите отдельный локальный экземпляр с тестовой БД:

```bash
APP_ENV=development DEMO_MODE=true BOT_TOKEN= DATABASE_URL=sqlite:///./razdelim-demo.db python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Откройте `http://127.0.0.1:8001/organizer?demo=1`, создайте тестовый сбор, затем перейдите по выданной локальной ссылке участника. Можно отметить тестовую оплату и открыть ссылку статуса. В демо используются фиксированные тестовые пользователи; страницы помечены, ссылки локальные и не работают в MAX. Demo-маркер принимается только при `APP_ENV=development`, `DEMO_MODE=true` и подключении с loopback. В production оставляйте `APP_ENV=production` и `DEMO_MODE=false`; это не замена MAX-аутентификации.

## Параметры и порты

| Переменная | Назначение | Значение примера |
|---|---|---|
| `APP_PORT` | Порт веб-приложения на хосте | `8000` |
| `POSTGRES_PORT` | Порт PostgreSQL на хосте | `5432` |
| `POSTGRES_USER` | Пользователь PostgreSQL | `razdelim` |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL | задайте свой |
| `POSTGRES_DB` | Имя базы PostgreSQL | `razdelim` |
| `DATABASE_URL` | Внутренний адрес БД; Compose формирует его для `db` | задаётся Compose |
| `BOT_TOKEN` | Токен бота MAX, используется для HMAC-проверки `initData` и Bot API | секрет организатора |
| `BOT_NAME` | Ник зарегистрированного бота; используется в startapp-ссылках | `razdelim_bot` |
| `MAX_API_BASE` | Базовый адрес Bot API | `https://platform-api.max.ru` |
| `MAX_WEBHOOK_SECRET` | Секрет входящих событий бота; должен совпасть с секретом webhook в настройках MAX | задайте свой |
| `MAX_INIT_DATA_MAX_AGE_SECONDS` | Максимальный возраст подписанного `initData` | `86400` |

Compose публикует `8000/tcp` для приложения и `5432/tcp` для БД. Чтобы изменить хостовые порты, задайте `APP_PORT` и `POSTGRES_PORT`.

## Архитектура и данные

- `app/main.py` — FastAPI, жизненный цикл БД, REST-маршруты, HMAC-аутентификация MAX и проверка владельца сбора.
- `app/security.py` — проверка подписи и срока действия `initData` по алгоритму MAX.
- `app/models.py` — SQLModel-модели сборов, участников и пользователей бота.
- `app/bot.py`, `app/max_sdk.py` — отправка сообщений и доступ к Bot API MAX.
- `static/` — HTML/CSS/JavaScript мини-приложения и страниц организатора.
- `Dockerfile`, `docker-compose.yml` — приложение и PostgreSQL; БД должна пройти healthcheck до старта API.

Данные сбора и участников хранятся в PostgreSQL в Docker volume `pgdata`. Тестовые сценарии создают записи запросами; отдельного набора реальных событий, туристических мест, спортивных объектов или внешней интеграции в MVP нет. Данные в демонстрации являются пользовательским вводом/тестовыми данными, а не сведениями из официальной системы. Для запуска в другом городе не нужны новые справочники в текущей версии; дальнейший каталог досуговых активностей потребует отдельного источника и проверки его актуальности.

Токен участника для `startapp` создаётся случайно и связывает ссылку с записью сбора. Организаторские операции требуют свежий подписанный `initData`; участник подтверждает свою запись тем же способом. Реквизиты и сведения о переводе не передаются платёжной системе.

Ядро для тиражирования — расчёт долей, приглашение участников и статус сбора. Первый пилот предлагается провести с одной студенческой или досуговой группой в одном городе; затем тот же сценарий можно подключать другим организаторам походов, встреч и спортивных занятий. Для этого нужны отдельный зарегистрированный MAX-бот/настройки доступа для контекста, HTTPS-хостинг и резервное копирование БД; городской каталог или внешние данные в текущем MVP не подключены. Это план масштабирования, а не уже выполненный запуск.

## API и интеграции

Собственный API нужен интерфейсу приложения; для оценки отдельный публичный API не заявляется. Основные маршруты:

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /health` | Проверка приложения и БД | публичный healthcheck |
| `POST /sessions` | Создать сбор и ссылку участникам | подписанный `init_data` организатора в JSON |
| `GET /sessions` | Список сборов владельца | заголовок `X-Max-Init-Data` |
| `GET /sessions/{id}` | Получить сбор владельца | заголовок `X-Max-Init-Data` |
| `GET /sessions/{id}/status` | Получить участников и отметки об оплате владельца | заголовок `X-Max-Init-Data` |
| `POST /join` | Присоединить пользователя MAX по `start_param` | подписанный `init_data` участника в JSON |
| `POST /confirm` | Отметить самоотчёт об оплате участника | подписанный `init_data` участника в JSON |
| `POST /webhook/max` | Обработать запуск бота и показать вход в мини-приложение | заголовок `X-Max-Bot-Api-Secret` |

MAX — единственная внешняя интеграция: Mini App launch data и Bot API. Если API MAX недоступно или тестового токена нет, реальные сообщения и проверка внутри MAX недоступны; локальные страницы можно открыть, но запросы без подлинного `initData` намеренно получают отказ. В MVP нет платёжного шлюза, каталога мероприятий, push-уведомлений об изменении событий или проверки банковских переводов.

## Подключение и проверка в MAX

Для прохождения основного сценария нужны зарегистрированный бот MAX, его токен, HTTPS-адрес приложения, настроенный адрес Mini App у бота и webhook на `https://<ваш-домен>/webhook/max`. Настройте секрет webhook в MAX и укажите тот же `MAX_WEBHOOK_SECRET`; токен бота и секрет не публикуйте. Укажите `BOT_NAME` точно как ник созданного бота. Без этих внешних настроек проект не считается доступным для проверки в MAX.

Проверочный сценарий после настройки:

1. Запустить бота и открыть созданный им экран организатора.
2. Создать сбор с тестовыми реквизитами; отправить полученную ссылку другому тестовому пользователю MAX.
3. Открыть ссылку участником, проверить сумму и реквизиты, отметить тестовую оплату.
4. Вернуться организатором на статус и проверить счётчик/статус участника.
5. Повторить открытие статуса другим MAX-пользователем: чужой сбор не должен раскрываться.

При локальном запуске без MAX проверяются `/health`, отдача статических страниц, валидация запросов и отказ неавторизованным пользователям. Подделывать `initData` или выдавать локальные страницы за интеграцию MAX нельзя.

## Тесты и ограничения

Зависимости зафиксированы в `requirements.txt`. Локальные тесты запускаются так:

```bash
python -m pip install -r requirements.txt
DATABASE_URL=sqlite:////tmp/razdelim-tests.db BOT_TOKEN=test-bot-token python -m pytest -q
```

Тесты используют синтетические подписанные данные, не рабочий MAX-токен. Известные ограничения MVP: нет платежной интеграции, управления отменой/возвратом, редактирования сбора и каталога досуга; новые поля существующих таблиц добавляются при запуске. Публичный HTTPS-хостинг, регистрация бота и доступ к MAX должны быть предоставлены командой отдельно.
